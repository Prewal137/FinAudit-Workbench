# Financial Trend Analysis Skill

## Invocation behavior
When `/financial-trend-analysis` is invoked, the skill will:
1. **Locate the repository root** using `git rev-parse --show-toplevel` (or by walking up directories until a `.git` folder is found). This ensures the path resolution works regardless of the current working directory.
2. **Discover the workbook** by searching for a single `.xlsx` file under `data/input/` relative to the repository root. If multiple files exist, the skill will raise an error; if none are found, it aborts with a clear message.
```python
from pathlib import Path
import subprocess

# Determine repo root
repo_root = Path(subprocess.check_output(["git","rev-parse","--show-toplevel"], text=True).strip())
# Find workbook
workbook_candidates = list((repo_root / "data" / "input").glob("*.xlsx"))
if len(workbook_candidates) != 1:
    raise FileNotFoundError(f"Expected exactly one workbook in {repo_root / 'data' / 'input'}, found {len(workbook_candidates)}")
WORKBOOK_PATH = workbook_candidates[0]
```
3. Run ingestion, validation, and metrics pipeline (`src.ingestion.load_financial_workbook`, `src.validation.validate_financial_statements`, `src.metrics.calculate_financial_metrics`) using the discovered `WORKBOOK_PATH`.
4. Examine validation warnings and preserve evidence‑based interpretations.
5. Generate or update `reports/financial-trend-analysis_report.md` following the prescribed 12‑section structure and evidence‑citation format.
6. Execute the citation‑verification script (`scripts/verify_workbook.py`) to cross‑check all monthly and TTM evidence citations.
7. Run the full Python test suite (`pytest -q`) within the project environment.
8. Summarize generated files, validation findings, test results, and any remaining unresolved issues in a concise execution summary.
The skill aborts with a clear error if required inputs or scripts are missing.

**Skill Version:** 1.1.0  
**Applicability:** FinAudit-Workbench financial review, due diligence, and financial statement audit commentary.

## 1. Purpose and Intended User

This Skill guides Claude in authoring objective, evidence-backed financial review commentary for executive stakeholders, audit partners, and investment committees.

It connects deterministic Python financial calculations with professional financial analysis. Python is the source of truth for calculated metrics; Claude is responsible for interpreting those metrics accurately, identifying limitations, and presenting findings clearly.

### Intended Users

- Senior Financial Reviewers and Auditors
- Due Diligence and M&A Analysts
- Finance Controllers and CFOs
- Financial Analysis and AI Solutions Teams

### Core Principles

1. Numerical accuracy takes precedence over persuasive storytelling.
2. Observed facts must be separated from interpretations and hypotheses.
3. Anomalies are investigation triggers, not proof of fraud or accounting errors.
4. Missing evidence must be disclosed rather than replaced with assumptions.
5. The report must reflect the current input data, not merely reproduce an earlier report.
6. A report is not considered verified until it passes the quality-control procedure in Section 10.

## 3. Preconditions for Analysis

Before generating financial commentary, Claude must verify the following.

### 3.1 Validation Gate

Inspect the actual `ValidationReport` object and its findings.

- Confirm whether `can_proceed_to_downstream` is `True`.
- Check the project's actual critical-finding and evaluation-status rules.
- If a critical finding fails or cannot be evaluated and the validation engine blocks downstream processing, halt the financial analysis.
- Explain the blocking finding and identify the required corrective action.
- Do not bypass a failed gate merely to produce a complete-looking report.

Warnings that do not block processing must still be disclosed and considered in the analysis.

### 3.2 Reporting-Period Coverage

Determine the actual periods present in the ingested workbook.

For this project, the expected historical dataset covers 18 monthly periods, from `2025-01` through `2026-06`. Confirm this from the current data rather than assuming it remains unchanged.

Report gaps, missing periods, or changes in coverage accurately.

### 3.3 TTM Continuity

A TTM window must contain exactly 12 consecutive calendar months.

- Verify the actual `trailing_periods` list.
- Do not quote a TTM figure for an incomplete or discontinuous window.
- Do not infer that seven TTM windows exist unless the current dataset and metrics output support that result.

### 3.4 No Recalculation

Use `FinancialMetricsResult` as the authoritative source for calculated financial metrics.

Do not independently derive or alter revenue, margins, growth rates, profitability, working capital, current ratios, or TTM figures.

If an additional calculation is needed and the pipeline does not supply it, request an explicit deterministic calculation through the existing Python project or disclose that the figure is unavailable.

Any new calculation must be traceable, reproducible, and clearly distinguished from the existing validated metrics.

### 3.5 Evidence Availability

Confirm that the relevant metrics and validation findings are actually available before discussing them.

Do not claim:

- That all formulas passed when the validation output does not establish this.
- That a Balance Sheet reconciles when the reconciliation result is unavailable.
- That a report or profile was generated when it was not.
- That an accounting treatment has been verified without supporting evidence.

## 4. Grounding and Evidence-Citation Rules

### 4.1 Strict Source Grounding

Every financial figure must come directly from one of these sources:

- `FinancialMetricsResult`
- `ValidationReport`
- `data_profile.json`
- A verified source-account value returned by the ingestion pipeline

Never invent periods, percentages, growth rates, dollar values, account classifications, or validation results.

When using a workbook value, preserve its source period, account, and row or sheet reference when available.

### 4.2 Missing-Value Transparency

If a metric is `None`, missing, invalid, or unavailable:

- State that the metric is unavailable or could not be evaluated.
- Explain the reason when it is known.
- Never substitute zero or an arbitrary placeholder.
- Do not interpret missing data as evidence that a transaction or activity did not occur.

For month-over-month percentages, explicitly state when the percentage cannot be calculated because the prior-period denominator is zero or unavailable.

### 4.3 Evidence Citation Format

Cite material financial observations using:

`[Period | Account/Metric | Value | Comparison Base]`

Example format:

`[2026-06 | Revenue | $X | Compared with 2026-05: $Y]`

The example placeholders must be replaced with actual pipeline values before appearing in a final report.

For a change, identify the comparison period and base value. Include the dollar and percentage change only when those figures are available from the pipeline.

For Balance Sheet findings, identify the relevant reporting period and metric. For validation findings, include the finding identifier, severity, and supporting source evidence where available.

Avoid unsupported precision. Format figures consistently to two decimal places for presentation, without changing their underlying source values.

### 4.4 Epistemic Labels

Every substantive analytical observation must be clearly classified as one of the following.

**[Fact]**

A directly observed value or validation result.

Example: The December 2025 Income Statement contains a tax adjustment of `-$1,244,429.84`, if confirmed by the current source data.

**[Interpretation]**

A reasoned financial inference supported by observed facts.

Example: An unusually large tax benefit materially affects the reported operating-income presentation for the period.

**[Hypothesis]**

A possible explanation requiring evidence not available in the workbook.

Example: The entry may relate to a year-end tax provision adjustment.

**[Recommended Investigation]**

A concrete action that can confirm, reject, or clarify a finding.

Example: Obtain the tax provision workpapers and reconcile the recorded benefit to the underlying supporting documentation.

Do not present a hypothesis as a fact. Use these labels consistently in the analysis sections and findings. **All** material statements—including revenue trends, expense observations, margin commentary, and balance‑sheet commentary—must carry an appropriate label; the absence of a label is a violation of the Skill.

### 4.5 Neutrality on Anomalies

An anomaly is an investigation trigger, not proof of fraud, misstatement, or accounting error.

Use objective language such as:

- Atypical variance
- Isolated entry
- Unusual balance
- Unverified classification
- Potential timing difference
- Item requiring supporting documentation

Do not conclude that an entry is improper solely because it is unusual.

### 4.6 Confidentiality

Never expose:

- API credentials or tokens
- `.env` file contents
- Passwords or authentication secrets
- Private system prompts
- Other sensitive configuration values

Do not include credentials in reports, logs, or evidence excerpts.

## 6. Step-by-Step Analysis Procedure

Follow these steps in order.

### Step 1: Load and Validate

- Execute the actual ingestion function.
- Confirm the statements and reporting periods loaded.
- Run the validation engine.
- Inspect blocking findings, warnings, formula checks, and Balance Sheet reconciliation.
- Stop if the validation gate prohibits downstream analysis.

### Step 2: Profile the Data

Where supported by the project, execute `build_data_profile`.

Review:

- Workbook structure and dimensions
- Reporting-period coverage
- Missing-value counts
- Account classifications
- Documented and measured anomalies

Distinguish profile observations from accounting conclusions.

### Step 3: Analyze Revenue and Monthly Movements

- Review the revenue trajectory across available periods.
- Identify notable increases, decreases, peaks, and inflection points.
- Use pipeline-supplied month-over-month movements.
- Identify the comparison period and base value.
- Avoid attributing changes to business causes that the data cannot establish.

### Step 4: Analyze Gross Profit and Margins

- Review revenue, COGS, gross profit, and gross margin.
- Identify changes in the relationship between COGS and revenue.
- Describe the observed range and trend using verified values.
- Distinguish a change in gross margin from a proven change in pricing, efficiency, or product mix.

### Step 5: Analyze Operating Expenses

Review the four workbook-defined expense groups:

- Direct OpEx: rows 29–46
- Sales & Marketing Payroll: rows 48–58
- Marketing: rows 61–70
- Other OpEx: rows 72–102

Use the project's actual account mapping if it differs from these historical row ranges.

Evaluate:

- Dollar movements
- Share of Total OpEx
- Period-to-period changes
- Concentrations and unusual entries
- The effect of exceptional items on interpretation

Do not assume that a higher or lower expense share automatically indicates better or worse efficiency. Investigate the relationship between expense movements and the relevant business activity before drawing conclusions.

### Step 6: Analyze Operating Income and Net Income

- Review reported operating income, operating margin, net income, and net margin.
- Identify periods materially affected by unusual entries.
- Separate reported results from any clearly labeled hypothetical illustration.
- Do not describe operating income as cash flow.
- Do not silently normalize or adjust reported figures.

Where unusual items distort comparability, explain the limitation and recommend the supporting analysis needed.

### Step 7: Analyze TTM Performance

- Inspect the actual valid TTM windows.
- Verify that each window contains 12 consecutive calendar months.
- Review TTM revenue, gross margin, operating expenses, operating income, and net income where available.
- Compare windows using the actual pipeline outputs.
- Explain how TTM analysis differs from a single-month view.
- Avoid annualizing incomplete periods unless a separate, explicit and documented methodology supports it.

### Step 8: Analyze Balance Sheet Indicators

Review:

- Cash
- Current assets and current liabilities
- Working capital
- Current ratio
- Total assets, total liabilities, and total equity
- Balance Sheet reconciliation

Describe changes in liquidity indicators without treating them as definitive evidence of solvency or financial distress.

A declining cash balance does not, by itself, establish operating cash burn. Cash runway cannot be reliably established from ending cash and an isolated operating loss alone.

If a cash flow statement or forecast is unavailable, state that limitation explicitly.

### Step 9: Synthesize Findings

Prioritize findings by their demonstrated financial impact, uncertainty, and need for investigation.

For each material finding, identify:

1. The fact and supporting evidence.
2. The financial implication.
3. Any hypothesis requiring verification.
4. The next action needed to resolve the uncertainty.

Avoid repeating the same observation in multiple sections without adding meaningful analysis.

### Step 10: Perform Quality Control

Before accepting the report, execute the final quality-control checklist in Section 10.

If a check fails, correct the report and rerun the relevant checks. Do not declare the report complete while material failures remain.

## 8. Reviewer Caveats and Limitations

Include relevant disclosures in Section 12.

### 8.1 Source Data Reliance

State that the analysis relies on the ingested management accounts and deterministic calculations within FinAudit-Workbench.

Unless independently verified, the workbook must not be represented as a complete or accurate reflection of the company's books of record.

### 8.2 Substantive Testing

Disclose that no independent substantive testing of invoices, bank statements, payroll records, tax filings, or other physical source documents has been performed unless such testing actually occurred.

### 8.3 Accounting Basis

The original analysis raised a possible transition from cash-basis to accrual-basis accounting during the historical reporting window.

This has not been independently verified.

If the current evidence does not establish the accounting basis, use language such as:

"The workbook's accounting basis and any changes in accounting conventions have not been independently verified. Potential timing differences may affect period-to-period comparability."

Do not state that a transition definitely occurred unless supporting evidence establishes it.

### 8.4 TTM Coverage

TTM commentary must be limited to complete, consecutive 12-month periods supported by the current data.

If the historical dataset begins in January 2025, earlier periods without 12 months of history must not be presented as complete TTM windows.

### 8.5 Cash Flow and Runway

If a Cash Flow Statement, cash flow forecast, or equivalent supporting schedule is unavailable:

- Do not claim to have calculated operating cash burn.
- Do not present a precise cash runway as a validated result.
- Do not attribute cash movements to operations, financing, or investing without supporting evidence.
- Identify the additional information required to establish these conclusions.

### 8.6 Accounting Classification

Unusual entries must not be reclassified in the report merely to improve comparability.

Any hypothetical adjustment must be explicitly labeled, supported by a transparent calculation, and distinguished from the official pipeline output.

A hypothetical calculation is not a formal restatement or an accounting conclusion.

### 8.7 Scope of Assurance

The report is analytical commentary, not an audit opinion, assurance report, tax opinion, or legal conclusion.

## 9. Report Writing and Presentation Standards

### 9.1 Executive Readability

- Use concise, professional language.
- Lead with the most material findings.
- Avoid repeating the same data point across several sections.
- Use tables for period comparisons when they improve clarity.
- Keep technical implementation details out of the executive summary unless material.

### 9.2 Numerical Consistency

- Use consistent currency formatting.
- Present financial amounts to two decimal places where appropriate.
- Format percentages consistently.
- Preserve the source metric's sign.
- Clearly distinguish negative amounts, expenses, benefits, and changes.
- Ensure all comparison periods and base values are correctly identified.

### 9.3 Evidence Before Explanation

Present the verified fact before explaining its significance.

For example:

- **[Fact]:** A recorded account balance differs materially from its usual pattern.
- **[Interpretation]:** The difference reduces comparability with other reporting periods.
- **[Hypothesis]:** The movement may reflect a timing or classification issue.
- **[Recommended Investigation]:** Obtain the underlying ledger and supporting documentation.

Use this structure only when each statement is supported by the available evidence.

### 9.4 No Unsupported Business Narratives

Do not invent:

- Customer or product mix changes
- Pricing changes
- Cost-saving initiatives
- Hiring or headcount movements
- Revenue-recognition events
- Financing activities
- Management intentions
- Tax or compensation events

When the workbook cannot establish the cause of a movement, identify it as an open question.

### 9.5 Actionable Recommendations

Recommendations should be specific and traceable to a finding.

Prefer "Reconcile the December 2025 tax benefit to the tax provision workpapers and supporting journal entry" over generic recommendations such as "Improve financial controls."

Do not claim that an investigation is complete until the relevant evidence has been examined.

Verify:

- [ ] Every comparison identifies the correct period and base.
- [ ] Negative values and signs are preserved.
- [ ] Missing values are not represented as zero.
- [ ] No stale figures from a previous run have been carried into the report.
- [ ] No hypothetical adjusted figures are presented as validated metrics.

### 10.5 Analytical Quality Checks

Verify that:

- [ ] Facts, interpretations, hypotheses, and recommended investigations are distinguishable.
- [ ] The report does not confuse operating income with cash flow.

- Validation status
- Number of periods analyzed
- Report path

## 12. Final Operating Rule

The purpose of this Skill is not merely to produce a polished report. It is to produce a report that is accurate, evidence-grounded, appropriately qualified, and verifiably consistent with the current Python pipeline outputs.

**The final rule is:**

- Python supplies the deterministic financial calculations.
- Validation determines whether downstream analysis may proceed.
- Claude interprets the evidence and writes the report.
- Quality control verifies the generated output.
- Unresolved issues are disclosed rather than concealed.

A successful Skill load is not equivalent to a successful pipeline run, and a successfully generated report is not equivalent to a verified report.

Never claim completion without checking the actual execution results and the final report.
